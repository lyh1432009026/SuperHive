# agy 在 Hive 里为什么慢

2026-11-25，rd #5932 转来用户反馈：「直接在反重力（agy）上做，3～5 分钟就好；让 cc 派给反重力做，反重力要执行 10～15 分钟。」这里记录实测对比、时间拆分、逐项排查的结果和这次的修改。

## 结论

- **Hive 自己的执行链路只多花 1～2 秒，不会让一件事慢上好几倍。** 实测：
  - 收到消息到 Bridge 开工 0.4～0.5 秒；
  - 拉起 agy、`initialize`、`session/new` 合计 0.6～0.8 秒；
  - 每次 `session/request_permission` 的裁决都在 1 毫秒内答复（9 次实测，平均 0.7 毫秒），没有排队、轮询或人为延迟；
  - agy 回复后发到房间 0.01～0.2 秒。
  - Claude 派活另外多两段时间，都是 Claude 自己的回合：派出去 5～39 秒，收到回执后总结 4～95 秒。
- **决定总时长的是模型要走多少步。** 这台电脑只能用 glm-5.3 冒充 Gemini（见下），这个后端经常「看不见」工具输出，于是反复重跑同一条命令。每多一步就多 5～15 秒。同一个任务：
  - 只发任务本身：5 次里 4 次 15～40 秒、2～4 步；
  - 带上 Hive 的规则或房间上下文：多数 200～475 秒、16～42 步。
  - 这是这个后端的毛病，和用户的 Gemini 没有可比性，所以这里**不能**据此说「Hive 的提示让 agy 慢了 10 倍」，只能说：在这个后端上，提示越长越容易陷进这种循环。
- **用户那边 3 倍左右的差距，最可能的原因**（按可能性排序，前两条在下面的排查里有依据）：
  1. **两边用的不是同一个模型或思考强度。** agy 交互界面记着用户上次选的模型（`last_selected_model_name`）；`agy acp` 开会话时用的是这个账号的默认模型。日志里写 `Setting default model override`：Google 账号默认 `gemini-4-hydrogen`、思考强度 high，API key 默认 `gemini-3.1-pro`、low。Hive 只有在 Agent 设置里选了模型时才会切换。以前 Hive 也不记 agy 每轮用了哪个模型，看不出来。**这次改成在每轮用量里记下实际的模型和思考强度。**
  2. **网络。** 0.4.7 及以前的客户端从访达或开始菜单打开时，agy 拿不到代理（945d88f 已修，0.4.8 起生效）。agy 连不上 Google 时会报网络错误，Bridge 按网络问题自动重试（等 30 秒、2 分钟、5 分钟……，每次从头再跑一轮）。用户看到的就是「做了很久」。本机实测：不走代理时 agy 换登录凭证、取模型列表都会超时。
  3. **派活的内容。** Claude 转述时如果说明写得太短，或者给的是它自己任务目录里的路径，agy 要么重新探索一遍，要么改到自己工作目录以外的文件。工作区档下改目录外的文件要交给人批，最长等 10.5 分钟（`approvalTimeoutMs`）。
  4. **会话越聊越长。** 以前每次带完整上下文的回合（每 8 轮或每 30 分钟一次），都把约 6300 字的整套规则再拼进 agy 会话的历史里，模型之后的每一步都得带着。**这次改成把规则放进 agy 的系统提示**，不再重复往历史里塞。
- **会话复用不是问题。** agy 进程本来就常驻，空闲 10 分钟才退出；会话用 `session/resume` 接上，不会每轮都从头开。分道以后，每件子任务各开一段新会话，这是有意设计的，开销只有上面那 0.6～0.8 秒。

## 测试环境和做法

- 本机 agy 1.5.14，macOS。这台电脑的 agy 没有可用的 Google 账号：rd 帮忙登录过一次（第一次授权码换凭证时直连 `oauth2.googleapis.com` 超时，改走本机 Clash 才登上），但账号调模型时 Google 返回 `403 LOCATION_NOT_ELIGIBLE`。出口是新加坡，问题在账号所在地区；换 Gemini 3.8 Flash 也一样。于是用 ACP 的 `logout` 退出登录，恢复原来的 API key。
- 所以两边都用同一个后端：`~/.gemini/.env` 里的 API key → 本机 LiteLLM → glm-5.3。agy 请求的所有 `gemini-*` 型号都映射到它。ACP 会话的默认值是模型 `gemini-3.1-pro`、思考强度 `low`、模式 `default`。**这个后端不是用户用的 Gemini，单次耗时的绝对值没有参考意义。**
- 任务：一个小仓库，`src/text.js` 里两个有 bug 的函数，`node --test` 跑 6 个用例。让 agy 把文件改成给定内容，跑 `npm test`，再用一句话说明改了什么。要改成的代码直接写在任务里，因为 glm 后端自己找 bug 时经常只读不改：第一次试跑 93 秒没改成。
- **A（直接跑）**：`agy acp` 加一个最小的 ACP 客户端，依次发 `initialize` → `session/new` → `session/prompt`，权限请求全部当场放行，相当于 Hive 的工作区档。`agy -p` 打印模式必须登录 Google，API key 只能走 ACP，所以 A 用的是 `agy acp`，不是交互界面。为了把 Hive 塞进去的内容和 Hive 的执行链路分开，A 还有几种变体：
  - **A-hive**：发 Hive 那一轮实际发出的完整文本，共 6306 字：规则 + 房间上下文 + 任务；
  - **A-sys**：规则放进系统提示，消息里只有房间上下文 + 任务，也就是这次改完后的样子；
  - **A-ctx**：只有房间上下文 + 任务，没有规则；
  - **A-rules**：规则放进系统提示，消息里只有任务本身。
- **B0（Hive 里直接 @）**：起一个临时 Server（127.0.0.1:18911，临时数据目录，`HIVE_LOCAL_AGENTS=0`），用 `hive join --provider agy --access workspace --cwd <仓库>` 接入 agy，人在房间里直接 @ 它。agy 外面包了一层脚本，把 stdin/stdout 上每行 JSON-RPC 带时间戳记下来，用来拆时间。
- **B（Claude 派活）**：同一个房间再接一个 Claude Code Agent（工作区档）。人 @ 它：「用 hive_invoke 把任务原样派给 agy1，等回执后告诉我结果」。
- 每次跑之前都把仓库还原，并删掉 agy Agent 的状态文件，保证每次都是新会话。「改前」的 B 是用上面那层脚本模拟出来的：把 `_meta` 去掉，规则拼回第一条消息前面，和改动前发给 agy 的内容一致。

## 两种跑法的时长

单位秒；括号里是工具调用次数；「没做完」指结束时 6 个用例没全过。

| 跑法                            | 各次总时长（步数）                                    | 中位数 |
| ------------------------------- | ----------------------------------------------------- | -----: |
| A 只发任务                      | 31（4）、40（2）、360（27）、31（4，没做完）、15（3） |     31 |
| A-hive：Hive 原样的提示         | 38（4）、309（20）、304（16）、75（4）、475（42）     |    304 |
| A-sys：规则放进系统提示（改后） | 206（19）、335（28，没做完）、291（25）               |    291 |
| A-ctx：只有房间上下文           | 360（40）、155（20）                                  |        |
| A-rules：只有规则（系统提示）   | 258（23）、366（26）                                  |        |
| B0 Hive 里直接 @，改前          | 89、158（14）                                         |        |
| B0 Hive 里直接 @，改后          | 35（4）                                               |        |
| B Claude 派活，改前             | 47（agy 35）、289（agy 272）                          |        |
| B Claude 派活，改后             | 368（agy 308）、284（agy 184）                        |        |

A-ctx 和 A-rules 各跑了两次，都慢：在这个后端上，不管多出来的是规则还是房间上下文，只要提示比任务本身长，就容易陷进循环。慢的那几次都是同一个样子：agy 跑完 `npm test`，又改成 `npm test > 文件` 再读文件、`echo hello`、`cat -A`……最后回复里写「本会话的工具输出捕获异常（cat/读取均返回空白）」。tee 记录显示 agy 发给客户端的 `rawOutput` 里输出完整，是 glm 后端那一侧没看到。只发任务时也出现过一次（360 秒、27 步）。所以表里的差距主要是这个后端的毛病，在提示长的时候更容易触发；不能拿来推断 Gemini 会怎样。

## B 的时间拆分

以 B0 改前第 2 次（158 秒，14 步）为例，Hive 这一侧：

| 段                                                       |                        耗时 |
| -------------------------------------------------------- | --------------------------: |
| 人发消息 → Server 建调用 → Bridge 开工                   |                     0.42 秒 |
| 拉起 agy、`initialize`、`session/new`（含注入 Hive MCP） |                     0.82 秒 |
| `set_config_option` 切模型                               | 0（没设模型，不发这个请求） |
| 6 次 `session/request_permission` 往返                   |               每次 ≤ 1 毫秒 |
| 模型思考、调工具、跑命令（agy 内部）                     |                      157 秒 |
| 回复发到房间、调用结束                                   |                      0.2 秒 |

B（Claude 派活）多出来的两段都在 Claude 那边：

| 次          | 人 → 派出（Claude 第一轮） | agy 执行 | 回执 → Claude 总结 | 总计 |
| ----------- | -------------------------: | -------: | -----------------: | ---: |
| 改后第 1 次 |                         39 |      308 |                 20 |  368 |
| 改前第 1 次 |                          7 |       35 |                  4 |   47 |
| 改前第 2 次 |                          5 |      272 |                 11 |  289 |
| 改后第 2 次 |                          5 |      184 |                 95 |  284 |

改后第 2 次 Claude 总结用了 95 秒：回执 0.4 秒内就交到 Claude 那里开工（调用记录 received → started），剩下的都是 Claude 这一轮自己的时间，不是 Hive 在等。Hive MCP 工具调用这次没有单独计时：B0 改前第 1 次 agy 用 `hive_message_send` 发了最终回复，消息发出后它又用了 4.4 秒才结束这一轮（模型收尾）；其余几次没用 MCP 工具。

## 逐项排查

- **权限**：工作区档下 agy 每次跑命令、改文件都发 `session/request_permission`，`AcpResponder` 同步裁决，当场答复。只有改工作目录**以外**的文件时才转给人批，这时会一直等到人点或超时（10.5 分钟）。实测任务里 agy 的改动都在工作目录内，没触发；往 `/tmp` 写文件走的是命令（execute），也直接放行。用户那边如果房间里出现了「申请权限」的提问，就是这个原因：派活时给的路径要落在 agy 的工作目录里，或者把 agy 改成完全权限档。
- **模型**：`agy acp` 没有指定模型的参数，会话打开时用账号的默认模型。Hive 的 `AcpResponder` 只有在 Agent 设置里选了模型时，才用 `session/set_config_option` 切换；没选就不切。交互界面另外记着上次选的模型，所以两边可能不一样，思考强度也可能不一样。现在每轮用量里都记下 `model` 和 `effort`（任务详情「本轮用量」能看到）。建议用户在 Agent 设置里把模型和思考强度选成和交互界面一样。
- **上下文**：
  - 新会话的第一轮：规则约 6300 字，加上房间上下文（总预算约 2.4 万 token），再加任务。
  - 子任务分道以后，每件子任务开一段新会话，第一轮只带分道说明、成员、白板、相关消息和任务，实测 1500 字左右，加上规则。
  - 以前的问题在长会话：主对话每 8 轮或每 30 分钟带一次完整上下文，每次都把整套规则再拼进消息，留在 agy 的会话历史里。agy 不报自动压缩，所以 Hive 只能按字符估算会话大小，换新也会晚一些。
- **会话**：进程常驻，空闲 10 分钟才退出，退出后下次用 `session/resume` 接上。同一进程里已经打开的会话直接用，不会每轮重新起进程。
- **网络**：agy 用 Go 的 `ProxyFromEnvironment`，只认环境变量。之前从访达打开的客户端不给 Agent 传代理，agy 直连 Google 会卡到超时；945d88f 起可以设置。本机日志里还能看到 agy 每 35 秒往 `play.googleapis.com/log` 发遥测，直连会超时，但这在后台进行，不挡回合。
- **人为延迟**：`AcpResponder` 没有轮询。权限裁决同步完成，Hive 工具（`mcp_hive_hive_*`）一律放行，`session/update` 来一条处理一条。唯一有意的等待是取消后的 10 秒宽限期。

## 这次的修改

1. **规则放进 agy 的系统提示**（`agy-client.ts`、`acp-responder.ts`）。agy 在 `initialize` 里声明了 `_meta.antigravity.systemPrompt.append`。现在打开会话（`session/new`、`resume`、`load`）时，把 Hive 的规则放进 `_meta.antigravity.systemPrompt.append`，追加到 agy 自己的系统提示后面，规则一样时不再拼进用户消息。规则在同一个进程里变了，会话已经打开、系统提示换不了时，退回拼进消息。实测（1.5.14）：
   - 追加的内容会随会话保存，进程重启后 `session/resume` 不带也还在；
   - `resume` 时带新的会替换掉旧的；
   - `_meta.systemPrompt`、`_meta["com.google.antigravity"]` 这两种写法不生效。

   这一条是让长会话不再越聊越长。在单次新会话的测试里没测出变快：A-sys 和 A-hive 一样慢，都是上面那个后端毛病。

2. **ACP 的回合用量记进 Hive**（`acp-responder.ts`）。agy、Gemini CLI 的 `session/prompt` 结果里带本轮总用量：`inputTokens` 含缓存读写，`totalTokens` 等于输入加输出。现在按 Hive 的四个桶（输入、缓存读、缓存写、输出）报给 Bridge，并带上会话当前的模型和思考强度，任务详情和用量统计里就能看到 agy 每轮用了哪个模型、多少 token、多长时间。ACP 不报请求次数，按「中间没有文字、相隔不到 1 秒的工具调用算同一次请求，最后出回答再算一次」来估。`peakContextTokens` 按平均值估。`effort` 字段的说明相应改成「Hive 传的，或运行时报出的会话当前值」。

没改的：权限快路径（已经是毫秒级）、会话复用（已经常驻）。Hive 规则本身的长度和措辞，比如服务器规则第 7 条「未经本机用户明确授权，不修改本地文件」和 Bridge 规则第 8 条的工作区授权字面上有冲突，这一条影响所有 Agent，不在这次范围里，另外提。

## 用户那边可以先查的

1. 在任务详情「本轮用量」里看 agy 用的模型和思考强度，和交互界面里的对一下；不一样就在 Agent 设置里改成一样。需要 0.4.8 之后带这次改动的版本。
2. 看任务卡片有没有「等待重试」或「可能需要配置代理」。有的话升级到 0.4.8，在「设置 → 这台电脑 → 网络代理」里配好。
3. 看房间里有没有 agy 发出的「申请权限」提问。有的话，派活时用 agy 工作目录内的路径，或者给 agy 完全权限档。
4. 派活时让 Claude 把文件路径、要改什么、怎么验证写清楚，别只写「按上面说的做」。
