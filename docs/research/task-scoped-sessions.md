# 方案：对话跟着任务走（task-scoped sessions）

> 状态：第 0 步、第 1 阶段已实现（分道、主道换新 + 规则交接摘要、每轮总预算，见文末「第 1 阶段实现记录」）；`kind=session` 消息、设置面板、任务道过滤、模型摘要未做。来源：rd #5612 同意的 #5608 改造顺序第 3 条，rd-claude #5615 委派。
> 分支：`feat/rd-claude2-task-scoped-sessions`（基于 main `f029667`）。

## 0. 现状与数据

### 现在会话怎么管

- Bridge 每个 (服务器, 房间, Agent, 运行时, 权限档) 一个状态文件（`state-store.ts`），里面只有**一个** `threadId`。
  人 @、主 Agent 接话、定时任务、别人 `hive_invoke` 派来的子任务、子任务回执，全部接在这一个会话上。
- 只有三种情况会换新会话：
  - 有人点「新话题」：`applyTopicBoundary` 删掉 `threadId`；
  - 房间换了工作区；
  - **任务目录变了**：`selectTaskWorkspace` 在 cwd 变化时整个删掉 `threadId`、`promptContext`、`instructionsDigest`。
    所以现在进任务目录、再回房间工作区，原来房间里那段对话也一起丢了。这是现有的一个隐性问题，本方案顺带修掉。
- 每轮附带的公共消息：`fetchMessages(lastProcessedSeq)` 把上一轮之后的全部消息都拉进来，每页 500 条，不设上限。
  `prompt-builder.ts` 只对单条做截断（正文 4000 字符、子任务结果 100000 字符），没有总量上限。
- 所有运行时都通过 `AgentReplyInput.threadId` 续接会话：Claude `--resume`、Codex `thread/resume`、ACP `session/resume|load`、Copilot `--resume`。
  所以「一个 Agent 有多段会话」可以全部在 Bridge 里做，各运行时的 responder 基本不用改。
- 服务端已经有判断「同一件活」的逻辑：`database.workAncestors(invocationId)`。
  回执、回复唤醒的那一轮算上游那件活的延续；别人新派来的委派是一件新活。任务目录就是按它来沿用的。

### 真实数据（本机 `agent_usage`，2026-11-17 起 7 天，Claude 运行时）

| 指标                                               | 数值                                  |
| -------------------------------------------------- | ------------------------------------- |
| 轮数 / 自报费用                                    | 1187 轮 / $4630                       |
| 每轮峰值上下文 p50 / p90 / p95 / 最大              | 33 万 / 84 万 / 92 万 / 99.9 万 token |
| 上下文 > 30 万的轮                                 | 638 轮（54%），费用 $3894（**84%**）  |
| 第一个请求写缓存 > 20 万的轮（缓存过期后重新续接） | 403 轮（34%），费用 $3236（**70%**）  |
| 被委派的子任务轮平均上下文                         | 26 万（子任务本来只需要任务说明）     |
| 人 @ 的轮平均上下文                                | 44 万                                 |

举一个典型的例子：某个 Claude Agent 空闲 5.8 分钟、5 分钟缓存刚过期，续接时一次写入 70.7 万 token 的缓存，这一轮花了 $4.08。

结论：钱和时间主要花在两件事上：**会话太长**，以及**长会话在缓存过期后被重新整段写入缓存**。把会话切短，两件事一起解决。

## 1. 会话怎么划分

### 1.1 分道（lane）

一个 Agent 在一个房间里不再只有一段会话，而是按任务分成几「道」，每道各有自己的运行时会话：

| 道     | 键                                   | 哪些消息进这一道                                                                           |
| ------ | ------------------------------------ | ------------------------------------------------------------------------------------------ |
| 主道   | `main`                               | 人直接 @、主 Agent 接话、定时任务，以及没有归属的消息                                      |
| 任务道 | 开启这件活的那次委派的 invocation id | 别人用 `hive_invoke` 派来的子任务，以及这件活后续的回执、回复唤醒、`hive_ask_human` 的回答 |

**归属由 Server 算，持久化在 invocation 上**，新增 `lane_key` 列。创建 invocation 时按下面的顺序决定：

1. 这条消息是回执、回复唤醒、提问的回答：沿用 `workAncestors` 链上那件活的 lane。
2. 这条消息是委派（`kind=delegation`）：
   - 同一个请求方、且请求方自己处在**同一件上游的活**里，也就是请求方的 work root 相同（例如 rd-claude 先派活，review 后再派「补改」）：复用之前那条 lane。这样「同一条委派链后续的返修、补充复用这段对话」就成立了；
   - 否则开一条新 lane。
3. 人发的消息，回复的（`replyToMessageId` / `parentMessageId`）是某条 lane 产出的消息，比如人直接在子任务交付下面回「再改一下」：进那条 lane。
4. 其余情况进 `main`。

Bridge 在快照的 `invocations` 里直接拿到 `laneKey`，不用多一次请求。**老 Server 不给 `laneKey` 时，一律按 `main` 处理，行为和现在完全一样。**

### 1.2 Bridge 状态怎么存

`AgentState` 新增 `lanes: Record<string, LaneState>`。原来顶层那些和会话绑定的字段挪进每一道：

```ts
type LaneState = {
  threadId?: string;
  cwd?: string;                 // 会话所在目录；Claude 的会话按目录存，换目录必须换会话
  promptContext?: …;            // rd-claude5 的成员/白板增量基线，按道存
  instructionsDigest?: string; briefTurns?: number; lastFullPromptAt?: string;
  lastTurnEndedAt?: string; lastRequestAt?: string; lastCacheTtlMs?: number;
  sessionCost?: { threadId: string; usd: number };
  seenSeq: number;              // 这一道上次看到的消息位置（给「增量 + 预算」用）
  contextTokens?: number;       // 上一轮的 peakContextTokens；运行时不报时按字符估算并标 estimated
  origin?: { messageId: string; requester: string; summary: string }; // 任务道的来由
  createdAt: string; lastUsedAt: string;
  handoff?: { fromThreadId: string; summary: string; at: string };     // 刚换新时带的交接摘要
};
```

- `inflight` 加 `laneKey`。崩溃后恢复时回到原来那一道，`crashResumes`、`interruptedSteps` 照旧按消息记。
- 最多保留 16 道，按 `lastUsedAt` 淘汰。已结束的任务道超过 7 天也淘汰。淘汰只是忘掉指针，不删运行时的会话文件。
- 迁移：读到没有 `lanes` 的旧状态时，把顶层字段包成 `lanes.main`。顶层 `threadId` 在两个版本内继续镜像主道，方便降级。

### 1.3 一轮里的调度

- **合批只合同一道的消息**。忙时陆续到达的几条 @ 不在同一道时，各自排队，一道一轮。
- **steer 只插同一道**：往 Codex `turn/steer`、Claude 流式输入、ACP steering 里插消息时，不是这一道的照常排队。
- Bridge 仍然一次只跑一轮，不引入并发。分道只决定这一轮用哪段会话。

## 2. 房间主对话自动换新 + 交接摘要

### 2.1 什么时候换

在某一道**开新的一轮之前**判断，从不在一轮中间换。同时满足下面两条才换：

- **是两个任务之间的空档**：这一轮的触发消息是一件新活，不是回执、回复唤醒、提问回答或中断续跑；这一道没有在等回执的子任务；也没有 `inflight`。
- **达到下面任一条件**：
  1. `contextTokens ≥ 换新阈值`，默认 **20 万**；
  2. 这一道空闲超过缓存时长（5 分钟或 1 小时），且 `contextTokens ≥ 10 万`。缓存已经没了，接着用旧会话等于把整段重新写一次缓存（上面那 34% 的轮、70% 的钱就是这么来的），换新反而更快更省。

任务道一般用不到换新：它一开始就是新会话。只有长任务道在两个阶段之间满足条件时才换，比如多轮返修越积越长。

### 2.2 和 rd-claude4 自动压缩的配合

- **换新管「两个任务之间」，压缩管「一个任务做到一半」**。两个都留，换新先触发。
- 约束：`换新阈值 ≤ 0.6 × 压缩阈值`。默认 20 万对 40 万。用户把压缩阈值改小时，换新阈值跟着往下压，界面上标出实际生效的值。
- 设置放在 rd-claude4 的「上下文与缓存」面板里，加一项「对话自动换新」：20 万（默认）/ 30 万 / 只在缓存过期后换 / 不自动换。这一项对所有运行时都生效，不只 Claude。
- 不能报上下文大小的运行时，按这段会话累计发出的提示和收到的回复的字符数来估，CJK 按 1 字≈1 token、其余按 4 字符≈1 token。界面上标「估算」。

### 2.3 交接摘要怎么生成

**分两期：第一期只用规则拼接，第二期可选加一段由模型写的摘要。**

| 方式                             | 费用                                                                                                                   | 延迟                                                        | 内容                                           |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- | ---------------------------------------------- |
| 规则拼接（第一期，所有运行时）   | 0                                                                                                                      | < 100ms，换新时现拼                                         | 结构化的事实                                   |
| 旧会话自己写一段（第二期，可选） | 约等于在这段会话上多问一个不调工具的请求：缓存是热的，主要是一次缓存读加 1～2k 输出，约为一个普通多步回合的 1/4 到 1/3 | 10～30 秒，在上一轮结束后的空闲里后台做，不占用人的等待时间 | 目标、决定、为什么这么做这类规则拼不出来的东西 |

规则拼接的内容上限约 6k token，各部分及来源：

- **目标**：这一道的 `origin`（触发请求原文前 1500 字、请求方），主道用最近一件人发起的任务。
- **最新决定**：这一道里人最近 5 条回复、`hive_ask_human` 的问答（问题和所选选项）。
- **我最近说了什么**：这个 Agent 在这一道最近 3 条最终回复，每条前 1500 字。交付消息里一般写着做到哪了。
- **未完成事项**：这个 Agent 名下没结束的 invocation，包括排队中、等人回答的，以及派出去还没回执的子任务；白板上这个 Agent 处在进行中或阻塞的条目。
- **工作目录、分支、提交号**：Server 已经登记的这个 Agent 的任务目录，包括 path、branch、HEAD、有没有未提交的改动、是否已合入。
- **验证结果和证据位置**：不复述，只给消息 `#seq` / `id` 和白板 key，需要时用 `hive_room_read` 补读。
- 上一轮的 `inflight.steps`，和现在 runtimeHandoff 那段一样。

第二期的模型摘要：上一轮结束时，如果这一道已经越过阈值、而且 Agent 空闲，Bridge 在后台对旧会话发一个固定提示，要求按上面的结构输出、不许调工具，Bridge 不把输出发到房间。这期间来了新消息就立刻中断，退回只用规则拼接。Server 不给这种回合发 invocation，Hive MCP 的写工具在没有 invocation 的回合里直接拒绝。

**为什么第一期不用模型**：规则拼接对所有运行时都一样可靠，没有额外费用，也不会和新到的消息抢时间。等第一期上线后，看人有没有抱怨「换新后忘了之前说的」，再决定第二期要不要做。

### 2.4 房间里怎么显示

- 新增消息类型 `kind: "session"`。它不唤醒任何人，不算话题分隔，只影响这一个 Agent 的这一道。
  正文是「rd-claude 换了一段新对话（上一段约 31 万 token），带上了交接摘要」，房主点开能看到摘要全文。
  摘要里有本机路径，所以只对房主展开，访客只看到这一行。
- 任务卡片的「本轮用量」里写明：这一轮在哪一道、是不是新会话、是不是刚换新。

## 3. 每轮附带内容设总量上限（prompt-builder）

`buildMentionPrompt` 现在是把 `messages` 全部格式化后拼起来。改成先选、再拼：

- **总预算**：默认 2.4 万 token（按 2.2 的规则估算），可用 `HIVE_PROMPT_BUDGET_TOKENS` 调。成员和白板单独计，rd-claude5 正在把它们改成只发变化的部分。
- **按优先级依次装入，装满为止**：
  - P0 触发消息：照旧完整给，单条截断规则不变。`subtask_results` 每条从 10 万字符降到 1.6 万，超出的部分给补读指引。
  - P1 触发消息的回复链：沿 `parentMessageId` / `replyToMessageId` 往上最多 5 条。
  - P2 未解决事项：@ 了我的消息；我提的问题和对它的回答；我派出去、回执还没处理的子任务。
  - P3 其余消息，从新到旧。
  - P4 装不下的：只给一行索引，形如 `#seq [发送者] 前 80 字…（全文 N 字）`。再往后的只写一句「另有 N 条较早消息（#a–#b）未附上，需要时 hive_room_read(afterSeq=…)」。
- **长内容只给索引**：不在 P0、P1 里的消息，如果正文超过 2000 字、主要是代码块或日志，降为一行索引，不占预算。
- **任务道的过滤**：任务道每轮只装和这件活相关的消息（P0～P2，以及请求方和这件活里其他参与者的消息），其余一律只给索引。主道照常。
- 每一道各自记 `seenSeq`：回到主道时，给的是主道上次之后的增量，再经过预算裁剪。
- 预算按「token 估算」算，字符串截断照旧注意代理对。补读指引的格式和现在的「正文预览已截断」保持一致。

## 4. 和现有功能怎么配合

| 功能                                | 怎么配合                                                                                                                                                                                                                                                             |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 新话题                              | 清掉这个房间的**所有道**，以及还没用上的交接摘要，和现在一致                                                                                                                                                                                                         |
| 任务目录                            | 每道绑定自己的 `cwd`。`selectTaskWorkspace` 不再删全局 `threadId`，只是这一轮去对应的道。在一道里切到新的任务目录（runtimeHandoff）= 这一道开新会话，并带上现有的 `previous_turn_summary` 加规则拼的摘要。回到房间工作区时，主道原来的会话还在（修掉现在会丢的问题） |
| 常驻进程（Claude keepalive）        | 换道时，要接的会话和常驻进程里的不是同一个，会按现有逻辑结束旧进程、另起一个并 `--resume`，多花 1～3 秒。但 prompt 缓存存在服务端，和进程无关，TTL 内照样命中。第二期可以让每个 Agent 最多常驻 2 个进程（主道 + 当前任务道），算进 rd-claude4 定的每台机器上限       |
| 自动压缩                            | 见 2.2：换新在任务之间先触发，压缩兜底任务中途                                                                                                                                                                                                                       |
| Codex / ACP / Copilot 等            | 都只是换一个传进去的 `threadId`。ACP 一个进程同时只挂一个会话，换道时多一次 `session/resume`。规则只能拼进用户消息的运行时，新会话会照旧带上 `refreshInstructions`                                                                                                   |
| 崩溃恢复 / 中断续跑                 | `inflight.laneKey` 保证回到原来那一道；续跑那一轮不算「两个任务之间」，不会换新                                                                                                                                                                                      |
| 「在终端里接着做」/ `reportSession` | 按道上报会话，任务详情里显示这条任务用的是哪段会话                                                                                                                                                                                                                   |
| 用量与费用                          | `sessionCost` 按道记，差分算本轮费用的逻辑不变                                                                                                                                                                                                                       |

## 5. 迁移和兼容

- **状态文件**：见 1.2，读的时候自动迁移，顶层 `threadId` 镜像两个版本。
- **Server**：`invocations.lane_key` 是可空的新列，老数据为空就当 `main`。protocol 的 `Invocation` 加可选字段 `laneKey`，消息 `kind` 加 `"session"`。
- **混合版本**：新 Bridge 配老 Server，全部走 `main`，跟现在一样。老 Bridge 配新 Server，忽略 `laneKey`，`kind=session` 的消息老网页按普通系统消息显示。
- **开关**：环境变量 `HIVE_TASK_LANES=0` 整体关掉，退回单会话。Agent 设置里「对话自动换新」可以选「不自动换」。
- **文档**：`docs/usage.md` 和排查文档（中英）补「对话怎么分道、什么时候换新、怎么关」。

## 6. 风险

| 风险                           | 缓解                                                                                                                                       |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 任务道看不到主道里聊过的背景   | 规则已经要求委派说明写完整；任务道带回复链和 `origin`；需要时自己 `hive_room_read`。上线后抽查「缺背景导致做错」的次数                     |
| 分道分错，比如返修被当成新活   | 返修复用规则看的是请求方和 work root；分错的代价只是少了些上下文，不会做错地方，因为任务目录另有逻辑。任务卡片标出用了哪一道，便于发现问题 |
| 换新后人觉得 Agent「忘了」     | 房间里显示换新消息，可以展开摘要；第二期加模型摘要；可以设成「不自动换」                                                                   |
| 换道多了，常驻进程反复重启     | 只多花 1～3 秒、缓存不受影响；第二期可常驻 2 个进程                                                                                        |
| 和 rd-claude4、rd-claude5 冲突 | 见第 8 节，排在它们合入之后改 bridge.ts 回合段和 prompt-builder                                                                            |
| 预算裁掉了关键消息             | P0、P1、P2 不受预算限制（只受单条截断）；被裁掉的消息都留了索引和补读方式                                                                  |

## 7. 验收指标

### 7.1 先补测量（第 0 步）

现在 `agent_usage` 里有上下文、缓存读写、费用和请求时间，但**没有首字时间**。先在 usage 里加 `firstTokenMs`（从开始执行到第一个文本或工具事件）和 `turnMs`，上线前跑一周作为基线。

### 7.2 场景基准

脚本 `scripts/bench-sessions.ts`：起一套临时 Server，回放一段固定的、约 50 万 token 的房间历史作为「老房间」，每个场景跑 10 次。用 Claude 和 Codex 各跑一遍。

| 场景       | 做法                            |
| ---------- | ------------------------------- |
| 短问答     | 老房间里人 @ 一个简单问题       |
| 连续开发   | 委派一个小改动，再追加 3 轮返修 |
| 长任务     | 一件要 30 次以上工具调用的活    |
| 空闲后恢复 | 空闲 6 分钟、70 分钟后各问一次  |

每个场景都记首字时间、整轮耗时、缓存命中率（`cacheRead / (input + cacheRead + cacheWrite)`）、每轮费用、峰值上下文，取 **p50 和 p95**，改动前后对比。

### 7.3 目标

| 指标                                   | 现在        | 目标     |
| -------------------------------------- | ----------- | -------- |
| 峰值上下文 p95（线上 7 天）            | 92 万       | < 30 万  |
| 子任务轮平均上下文                     | 26 万       | < 5 万   |
| 「缓存过期后整段重写 > 20 万」的轮占比 | 34%         | < 5%     |
| 每轮平均费用（线上 7 天）              | $3.9        | 降 ≥ 50% |
| 短问答首字时间 p95                     | 待第 0 步测 | < 8 秒   |
| 空闲后恢复首轮费用                     | 待测        | 降 ≥ 70% |
| 分道正确率（人工抽查 50 轮）           | —           | ≥ 95%    |

线上对比用 `agent_usage` 前后各取 7 天。

## 9. 第 1 阶段实现记录（feat/rd-claude2-task-lanes）

按 rd-claude #5906 的四件做，把原方案第 1 阶段和第 2、3 阶段里不依赖界面的部分合在一起：

- **分道**：Server 在 `createInvocation` 里按 1.1 的规则算 `lane_key`；Bridge 没有另起 `lanes` 结构，而是沿用已有的 `parkedSessions`（按目录收起会话），键从「目录」扩成「目录 + 道」，当前道记在 `state.lane`，最多 16 段、超出先丢子任务道。这样旧状态文件不用迁移，顶层字段就是当前那一道。
- **主道换新**：只在主道、两件活之间；「没有在等回执的子任务」用最近 300 条消息里自己发出的委派有没有回执来判断。阈值和设置项先用环境变量，没有做「上下文与缓存」面板里的选项。
- **交接摘要**：只用规则拼，素材是房间消息（最近交给它的事、人最近说的、它最近的回复、没回执的子任务、工作目录），没有接白板和任务目录登记。换新时在任务卡片进度里写一句，没有发 `kind=session` 消息。
- **总预算**：按 3 节的优先级做了 P0～P4 和长消息只给索引，`subtask_results` 降到 1.6 万字符；任务道过滤没做（任务道本来就是新会话，附带的只有增量）。
